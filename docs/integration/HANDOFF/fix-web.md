## 1. Менеджер API-ключей (F29)

**Было.** `grep -in "api-key|apikey|bootstrap|secret" proxy_workbench/ui/app.js`
→ 0 совпадений. В `gui.py` среди ~60 маршрутов `/api/*` не было ни одного про
ключи. `proxytool.py` печатал в терминал `…/proxies` — устаревший адрес, без
`/v1` и без единого слова о ключе. При этом `apikeys.py` (1479 строк) был
написан, покрыт тестами и полностью недостижим из GUI, который и есть точка
входа по умолчанию.

**Стало.** Поверх готового `apikeys.ApiKeyManager` (не переписывая его):

| Маршрут | Что делает |
|---------|-----------|
| `GET /api/api-keys` | список без секретов + права, которые можно выдать + журнал операций |
| `POST /api/api-keys` | выпуск ключа с правами, scope и сроком |
| `POST /api/api-keys/bootstrap` | первый админ через локальную доверенную поверхность |
| `POST /api/api-keys/action` | `rotate` / `update` / `disable` / `enable` / `revoke` / `delete` |
| `GET /api/gateway/options` | пулы и профили для привязки шлюза |
| плюс | `nav-key-count` в боковой панели, deep-link `{url}#keys` |

Страница «Ключи API» (`#page-keys`, вкладка в сайдбаре): первый админ, карточка
секрета с явным предупреждением «показывается один раз», выпуск с выбором
прав (пресеты «только чтение» / «полный»), список с ID, префиксом, сроком,
последним использованием и состоянием, кнопки ротации / отключения / включения /
отзыва / удаления, журнал операций.

**Модель доверия — важно для ревью.** Интерфейс локально доверен: он держит
блокировку папки данных, токен сессии minted на запуск, и каждый запрос обязан
прийти с `127.0.0.1` и с этим `Host`/`Origin`. Поэтому:

* `bootstrap` не требует секрета — ровно как `api-key bootstrap` в CLI;
* всё остальное идёт через настоящую проверку прав модуля. Актор — либо
  административный секрет, который пользователь вставил в поле на странице
  (живёт только в памяти страницы, никогда не пишется в файл и в журнал), либо
  старейший активный административный ключ установки
  (`App.key_admin_actor`). Журнал аудита в обоих случаях называет этот ключ.
  Если админа нет — отказ с текстом, а не молчание.

**Стартовая строка при запуске.** `gui.main()` печатает

```
API для своих программ: http://127.0.0.1:8765/v1 (ключ — на странице «Ключи» в интерфейсе, http://127.0.0.1:PORT/#keys)
Ключей API нет: выпустите первый на странице «Ключи» в интерфейсе.
```

и, если админ уже есть, `Ключей API: N административных.`

## 2. Импортёр F03

**Было.** `gui.py` не содержал ни одного упоминания `importer`,
`import_preview`, `import_commit`, `import_source`, `import_client_config`.
Собственный список — это `textarea#proxies` плюс file-drop, который кладёт текст
в textarea, а кнопка шлёт его в `/api/collections/members` →
`App.add_collection_members`, который пишет membership напрямую. Ни предпросмотра,
ни номеров отклонённых строк, ни сопоставления колонок, ни merge/replace, ни
отмены, ни отчёта. `index.html:1439` ограничивал `accept=".txt,.list,text/plain"`.
`importer.py` (1162 строки) был доступен только из CLI.

**Стало.** `POST /api/import/preview`, `POST /api/import/commit`,
`GET /api/import/batches` поверх `importer.preview` / `importer.commit` /
`importer.load_report`. Плюс карточка «Импорт списка из файла, с предпросмотром»
на странице «Источники»:

* выбор файла (`.txt .list .csv .tsv .json`) **или** вставка текста;
* список назначения (тот же, что у коллекций), формат (auto/txt/uri/csv/json),
  режим (merge / replace);
* предпросмотр: valid / duplicates / rejected, **номера отклонённых строк**,
  образец строки, код причины, отпечаток файла, batch id, что будет добавлено /
  уже есть / будет удалено;
* сопоставление колонок для CSV, когда заголовок неоднозначен: страница получает
  `mapping_suggestion` от `importer.MappingSuggestion` и показывает выпадающие
  списки по колонкам файла с предупреждением на неоднозначных ролях;
* отчёт после применения + история импортов.

**Инварианты, которые проверялись живьём:**

* предпросмотр не пишет ничего — `members.total` остаётся 0;
* `commit` применяет **тот самый** объект `Preview`, который показала страница
  (план хранится в `App._import_plans` по `batch_id`; `Preview` нельзя
  восстановить из JSON, поэтому это единственный способ сделать «применить»
  теми же числами, что на экране);
* повторный `commit` того же плана возвращает `replayed: true` и не добавляет
  ничего (идемпотентность F29 на стороне модуля);
* колонка с логином/паролем по-прежнему отклоняется (`E_IMPORT_CREDENTIALS`).

**Два бага, найденных при живой проверке и исправленных здесь:**

1. `busy` в `importer.commit` — это **callable**, а не строка. Первая версия
   отдавала `core._busy_collection(...)` напрямую → `TypeError: 'str' object is
   not callable` на любом commit. Сейчас причина читается **до** взятия
   write-lock'а и передаётся как `lambda: reason`: открывать второе соединение
   к файлу, который уже держит писатель, нельзя.
2. `Preview.to_dict()` отдаёт `mapping_problem`, но **не** `mapping_suggestion`,
   а странице без предложения не из чего построить выбор колонок.
   `App.import_plan_view` добавляет предложение из `plan.mapping_suggestion`.

## 3. Пулы, расписания, привязка шлюза (F14, F15)

**Было.** В `gui.py` нет ни одного маршрута для pools и ни одного для
schedules. Шаг «1. Pool» на странице шлюза печатал число из опубликованного
экспорта, а `App.gateway_state` брал пул из `status.json`. `proxytool run_gateway`
не умеет `--pool`. Именованные пулы и расписания жили только в CLI и `/v1`.

**Стало.**

| Маршрут | Что делает |
|---------|-----------|
| `GET /api/pools` | список пулов со статусом; `?id=` — один пул с участниками |
| `POST /api/pools/create` | создание с desired / minimum / reserve |
| `POST /api/pools/action` | `start` (запуск **и** наполнение), `pause`, `refill`, `target`, `policy`, `recheck`, `member-remove`, `member-state` |
| `GET /api/schedules` | расписания с ближайшим запуском, счётчиками и историей |
| `POST /api/schedules/action` | `add`, `enable`, `disable`, `pause`, `resume`, `run-now`, `remove` |
| `GET /api/gateway/options` | пулы, профили, текущая привязка |
| `POST /api/gateway/config` | привязка шлюза к пулу и профилю + перезапуск слушателя |

Всё это те же вызовы, что делает `/v1` (`workbench.pool_refill`,
`api.pools_state_for`, `api.pool_candidate_source`, `scheduler.Scheduler`), чтобы
не было второй реализации пополнения пула.

Страница «Пулы и расписания» (`#page-pools`): создание пула, список с
`served/desired`, состоянием, причиной нехватки (`deficit_reasons` с кодами и
счётчиками) и готовностью для клиентов; карточка выбранного пула с целями,
кнопками «Запустить и наполнить», «Пополнить сейчас», «Перепроверить список»,
«Пауза», «Сохранить цель» и списком участников; расписания с ближайшим
запуском, причиной, счётчиками, вкл/выкл, «Запустить сейчас», удалением;
карточка «Что отдаёт ротирующий прокси» с выбором пула, профиля, ревизии и
поколения.

**Две честные оговорки, которые стоит знать ревьюеру:**

* `pools.refill` на честных данных может вернуть `served: 0` с
  `deficit_reason: E_TIME_TTL_MISSING` — это модуль отказывает кандидату без
  `valid_until`. Маршрут показывает эту причину, а не «0 успешно».
* У расписания, которое ещё ни разу не запускалось, нет базового момента для
  интервала, и `Scheduler.plan` отвечает «not due, следующего запуска нет».
  Таблица `schedules` (миграция 7) не имеет `activated_at`, и
  `SqliteScheduleStore.load_state` его не восстанавливает. Интерфейс помнит
  момент создания расписания в своём сайдкаре `gui-schedules.json` и отдаёт его
  модулю; **сам** план считает `scheduler.Scheduler.plan`, а не страница.

**Привязка шлюза** — это `gateway.Binding(pool_id, generation, profile_id,
profile_revision, policy)`, который `gateway.Pool._bound_rows` действительно
применяет: несовпадение поколения или профиля даёт пустой набор строк. Выбор
пула, которого нет, отклоняется с текстом, а не сохраняется молча.

## 5. Четыре маршрута, отвечавшие «ок» без работы

**Было.** Воспроизведено живым запросом: все четыре отдавали 200 с
фиксированным телом.

| Маршрут | Старое тело | Что делает теперь |
|---------|-------------|-------------------|
| `POST /api/sources/recover` | `{"id":…,"cleared":1,"recovered":true}` | `cleared` — сколько строк `candidate_meta` источника реально удалено; следом идёт **один настоящий запрос** `preview_source` и в ответе `check: {http_state, status, recognized, complete, error}`. Источника нет в каталоге → `recovered: false` и текст «восстанавливать нечего». Проверка отказала (например, формат не собирается) → `recovered: true` **и** `check.http_state: "refused"` с текстом: восстановление наполовину случилось, и это сказано прямо |
| `POST /api/sources/exclude-scope` | `{"excluded":0,"delivered":0,"shared":0,"already_excluded":0}` | Считает `candidate_seen` по ключам источника, делит на «доставил только этот источник» и «доставили и другие». По умолчанию исключаются только эксклюзивные; общие требуют явного `include_shared` (source-system-design §12.3). Возвращает реальные `delivered / exclusive / shared / excluded / already_excluded` |
| `GET /api/sources/scope` | `{"count":0,"proxies":[]}` | Реальный список: адрес, источник, «общий», момент. Есть `sources` для кнопок «вернуть адреса этого источника» |
| `POST /api/sources/scope/clear` | `{"removed":0}` | Реальное `removed` и `remaining` |

**Где хранится.** `db.py` не имеет таблицы `candidate_scope_exclusion` — её
нет вообще в миграциях; единственная ссылка на неё есть в
`source_management.py:239`, внутри `try/except sqlite3.Error`, то есть она
молча не работает. Добавлять DDL в `db.py` я не могу, поэтому исключения лежат
в сайдкаре интерфейса `gui-scope-exclusions.json` — рядом с тегами, заметками и
сохранёнными представлениями, то есть как пользовательский документ.

**Исключение не декоративное.** Оно применяется в `App.scoped_rows` — в единственном
месте, через которое проходят и таблица результатов, и экспорт интерфейса.
Проверено живьём: 3 строки в таблице → исключение эксклюзивных адресов →
в таблице 1 строка → включение `include_shared` → 0 строк → очистка → снова 3
строки (ничего не удалялось, адреса на месте).

Одно тонкое место, которое стоит знать: `candidate_seen.proxy` хранит адрес так,
как его опубликовал список (`198.51.100.1:8080`), а строка результата и
`endpoints.canonical` — нормализованный (`http://198.51.100.1:8080`). Исключение
хранится в нормализованном виде, иначе список был бы прав, а из таблицы ничего бы
не уходило.

**Диалог.** `#scope-dialog` в `index.html` существовал с первой версии и имел
только обработчик закрытия — `showModal()` не вызывался нигде. Теперь он
открывается кнопкой «Исключённые адреса…» в блоке «Ваша область» на странице
«Источники», показывает реальный список и кнопки «Вернуть адреса этого
источника» / «Вернуть все».

## 6. `diagnose health` печатает ложную тревогу — чужой файл

`HealthCheck.to_dict()` (`proxy_workbench/diagnostics.py:1596-1598`) отдаёт
булево поле `ok`, поля `state` нет. Фильтр в `proxy_workbench/proxytool.py`:

```
proxy_workbench/proxytool.py:4467
        problems = [item for item in body.get('checks', []) if item.get('state') != 'ok']
```

`item.get('state')` для каждой проверки даёт `None`, `None != 'ok'` истинно, и на
исправной базе печатается «5 checks, 5 problems».

`proxytool.py` мне не принадлежит (в момент написания этой карточки файл
правит параллельная работа), поэтому строка записана здесь точной строкой, а не
исправлена. Исправление — одна строка, по смыслу:

```python
problems = [item for item in body.get('checks', []) if not item.get('ok')]
```

или, если `state` должен стать частью контракта, — добавить `state` в
`HealthCheck.to_dict()` в `diagnostics.py` (тоже чужой файл). Первое ничего не
ломает: `HealthReport.ok` уже считает `all(check.ok ...)`.

Отдельно отмечу для владельца `proxytool.py`: во время этой работы файл был
изменён параллельной правкой и **переставал парситься** —
`proxytool.py:1938: SyntaxError: no binding for nonlocal 'completed' found`,
из-за чего `tests/test_selection.py` падал, а любой запуск подпроцесса
интерфейса (`App.start`) завершался с кодом 1. На момент сдачи этой карточки
строка уже исправлена, но проверяющему стоит знать, что это была.
