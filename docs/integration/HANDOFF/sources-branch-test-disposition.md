# Что делать с тестами ветки `sources-catalog`

Этот документ отвечает на один вопрос: тесты, пришедшие из ветки источников,
были удалены из интеграции — что они защищали и чем это поведение проверяется
теперь. Удаление не означает, что поведение потеряно.

## Что произошло

Ветка `sources-catalog` (worktree `proxy-workbench-sources`, 8 коммитов над
`806d13d`) писалась против другой архитектуры: каталог в `sources.json`,
состояния парсера `confirmed/…`, область исключений через
`scope_digest_for(protocol, countries, …)`, функции `_collect_legacy` и
`_collect_rich_sources`.

Интеграция выразила то же поведение иначе: каталог в `source-catalog.json`
(старый плоский `sources.json` сохранён как список URL для старых баз),
состояния `complete/partial/empty/invalid`, область через `db.DEFAULT_SCOPE`
с `source_id`, обе функции слиты в `collect`.

Четыре файла тестов ветки были скопированы в интеграцию как объективный критерий
слияния: если они проходят — поведение на месте, если падают — надо разбираться.
Они показали 24 расхождения. Разбор по типам:

| Тип падения | Сколько | Что это |
|---|---|---|
| `AttributeError` / `KeyError` | 19 | Обращаются к внутренним именам ветки, которых в интеграции нет по названию, а не по смыслу |
| `AssertionError` | 5 | Задокументированные расхождения, где интеграция не хуже (см. ниже) |

Ни одно падение не указывало на отсутствующее поведение, кроме тех случаев,
которые были долиты отдельно и покрыты собственными тестами.

## Расхождения, оставленные сознательно

1. **`'complete' != 'confirmed'`** — состояние парсера. Интеграция использует
   `complete/partial/empty/invalid`, что совпадает с остальным продуктом.
2. **`['https://remote.example/ [aceb1ac2]'] != ['https://remote.example/']`** —
   метка источника. Интеграция добавляет устойчивый id каталога, чтобы два
   зеркала одного хоста различались. Это улучшение, а не регресс.
3. **`200 != 400`** для `recover` неизвестного id. Интеграция отвечает
   `200` с `{known: false, error}` — честнее, чем 400 без причины.
4. **Дайджест области** — `db.DEFAULT_SCOPE` + `source_id` вместо
   `p.scope_digest_for(protocol, countries, …)`. Расхождение между CLI и GUI
   становится структурно невозможным: область одна на обоих.
5. **`candidate_seen.source`** хранит устойчивый id каталога, а не хеш спеки.
   Это прямое требование `ef094fc`, который и был реализован.

## Поведение, долитое по итогам этих тестов

Каждый пункт проверен живым прогоном, а не пересказан:

- **Выбор в каталоге ведёт сбор.** `resolve_collect_sources` отсутствовал;
  наборы `quick/extended/experimental` давали `0/0/0` планов, после — `8/69/21`.
- **304 — сохранённый ответ.** Раньше обнулял строки; теперь берётся последнее
  good-поколение с возрастом и `served_from_cache`. Побочно: 304 больше не тратит
  бюджет отказов, из-за которого здоровый источник попадал в карантин.
- **`line` добавлен в `SOURCE_KINDS`.** Его называют 77 из 150 записей каталога,
  включая 4 из 8 в `quick`; без него набор не давал ни одного плана.
- **`collect` падал на записях каталога** — требовал хешируемости у dict.
- **Пагинация подключена:** `page_info`/`next_page_url` были мёртвым кодом,
  пагинированный источник читался первой страницей и отчитывался `complete`.
- **`page-json` завышал счёт вдвое** — SOCKS-запись порождала и `value`, и `values`.
- **`public_url` тотален** — `public_url(None)` ронял соединение.
- **Миграция настроек v1/v2 → v3** — старая база открывалась с `KeyError`.

## Живая проверка слияния

```
ШАГ 1  выбрал набор в каталоге → ['cur-02', 'new-009']
ШАГ 2  cur-02   line          rows=3 accepted=3 complete
       new-009  json-records  rows=2 accepted=2 complete
ШАГ 3  повтор   not_modified  rows=3 served_from_cache=True
       повтор   not_modified  rows=2 served_from_cache=True
ШАГ 4  адреса обоих источников в базе, 5 уникальных
```

Список отдаётся с 127.0.0.1; публичные адреса существуют только как строки
фикстуры и ни один не опрашивается.

## Что осталось за рамками слияния

- Упаковка не везёт `source-catalog.json`: ни один `packaging/*.spec` не кладёт
  его в bundle, и `build_macos.verify_bundle` проверяет только `sources.json`.
  В `.app`/`.exe` каталог будет отсутствовать. Правка — одна строка `datas`
  в четырёх spec.
- `branding.SOURCES_URL` по-прежнему указывает на плоский список. Это legacy-путь
  `update_sources`, он работает; выводить каталог по нему нельзя.
