# HANDOFF: владение файлами и передача изменений

**База:** ветка `integration/ultra-2026-09-25`, HEAD `9406372`, документ пересмотрен 25 сентября 2026 года после замечаний независимого критика.
**Сопутствующий документ:** `docs/integration/CONTRACTS.ru.md` — источник истины по идентичностям, схеме, freshness, snapshot, API и состояниям job. Здесь — только владение файлами и порядок передачи.

## 0. Правило

**У изменяемого файла ровно один writer.** Исполнитель, которому файл не принадлежит, его не редактирует — ни частично, ни «на пять минут», ни «там одна строчка». Он приносит изменение через `docs/integration/HANDOFF/<имя>.md`, и файл правит владелец.

Это прямо следует из MASTER-PROMPT §1: «`proxytool.py`, `gui.py`, `api.py`, общая БД и центральные UI-файлы нельзя редактировать конкурирующим набором исполнителей. Минимальное выделение реальных модулей допускается для устранения конфликтов, без массовой переписи».

**Минимальное выделение новых модулей — да. Массовая перепись существующих файлов — нет.** Новый leaf-модуль (`db.py`, `jobs.py`, `secrets.py` и подобные) — это нормальный способ распараллелить работу. Копирование чужого модуля к себе, второй движок сканирования, вторая БД, второй worker-протокол — это не выделение, это дублирование, и на интеграции оно удаляется.

**Как читать этот документ.** Таблица §1 описывает владение **по фактическому** содержимому `.zcode/workflow-drafts/ultra-2026-09-25.dwf.ts`. В сценарии четыре группы: `AREAS` (`:133`, только чтение), `BUILDS` (`:345`, 18 новых файлов), `SURFACES` (`:711`, всего два агента — `gateway` `:713` и `web` `:734`) и `integrator` (`:811`). Придуманных поверхностей в сценарии нет; первая редакция этого документа описывала роли, которых не будет, и переписана. Каждая строка §1 указывает источник назначения — из сценария или из этого документа. Три расхождения, которые сценарий разрешить не может, вынесены в §8.

### 1.4 Конфликт `gui.py` и `ui/*` и его разрешение

Сценарий отдаёт `gui.py` и три файла `ui/*` поверхности `web` (`:737-738`), а интегратору — только `proxytool.py` и `api.py` (`:823-824`). MASTER-PROMPT §1 требует одного writer'а на изменяемый общий файл. Два назначения на шесть файлов — конфликт того же класса, что был зафиксирован ранее, и он не разрешается в пользу времени.

**Принятое разрешение — вариант A с выделением F19 в отдельные файлы.** Оно не требует переписывания сценария для уже выданных зон и снимает главный практический риск: F19 — это page/selected/all-matching scope, bulk recheck/export/copy/tag/exclude/denylist, теги, избранное, заметки, saved views и колонки, матрица proxy×target и представления fresh/stale/failed/unknown. Это не «точечное добавление» в 233 КБ `app.js` + 90 КБ `index.html` + 144 КБ `style.css` (проверено `wc -c`), а объём, который через 18 прозаических handoff'ов «применить» нельзя.

| Кто | Что пишет |
| --- | --- |
| Поверхность `web` | `gui.py`, `ui/app.js`, `ui/index.html`, `ui/style.css`, `i18n.py` — как выдано сценарием `:737-738` |
| Новый исполнитель `ui-views` | Только **новые** файлы `proxy_workbench/ui/views/*.js` (результаты, матрица, представления, saved views) и свои тесты `tests/test_ui_views_*.py`. Он не редактирует существующие файлы `ui/*` |
| Интегратор | `proxytool.py`, `api.py` — как выдано `:823-824`. В `gui.py` и `ui/*` он **не пишет**, а только принимает решения о стыке, если поверхность `web` передаст их через handoff |

Переход `ui-views` на существующие файлы `ui/*` — только через handoff и только по решению интегратора, с указанием конкретного контейнера и существующих классов. Общий редизайн, смена тем и переписывание layout запрещены в любом из этих вариантов (MASTER-PROMPT §0).

**Что снимается из первой редакции этого документа.** Правило «правки в `gui.py` и `ui/*` не коммитятся ни одной из сторон, а копятся в handoff» удалено: у него нет исполнителя, передать его в сценарий нечем, а workflow всё равно будет коммитить, поэтому оно цено и разрушает работу поверхности. Взамен — вариант A выше: у `gui.py` и `ui/*` есть ровно один writer (поверхность `web`), у F19 есть собственный файловый домен, у интегратора нет общих файлов с поверхностью.

## 2. Модульные исполнители: 18 новых файлов, две волны

Каждый модуль — **leaf-файл, единственный writer — его автор**. Он не импортирует и не мутирует чужие модули без явной точки входа; он экспортирует чистые функции и узкие типы, на которые ссылаются остальные. Каждый ведёт `HANDOFF/<имя>-handoff.ru.md` и свои тесты `tests/test_<имя>_*.py`, запускаемые командой `.venv/bin/python -m unittest tests.test_<имя>`.

### 2.1 Волна 1 — только `db.py`

Первая редакция этого документа предлагала «схему своей таблицы модуль объявляет в handoff, а создаёт через миграционный раннер `db.py`». **Это правило удалено:** заявка в прозе не проверяется, поэтому семнадцать модулей, работающих в одной волне, всё равно разойдутся в представлениях схемы — ровно тот отказ, который сам документ называет самой дорогой ошибкой этапа.

Вместо этого:

- **`db.py` запускается один и только один раз, первым.** Он получает весь `CONTRACTS.ru.md` §3.3 как спецификацию и обязан реализовать **исполняемые** миграции `0..14` плюс `SCHEMA_VERSION = 14`, а не описание миграций.
- Обязательные тесты `db.py`, каждый на временной БД:
  1. открытие базы с `user_version = 0` (созданной текущим `open_db`) и полная миграция `0..14`;
  2. повторный запуск на уже мигрированной базе — ни одного изменения;
  3. отказ при `user_version > 14` — и **ни одной записи**, включая сам `user_version`;
  4. отказ при чужом `application_id`, отличном и от 0, и от магического числа;
  5. пересборка `results` (миграция 13) реально меняет `PRIMARY KEY` и разводит две строки одного `(profile, proxy)` с разными `access_revision` по разным строкам;
  6. пре-миграционный backup создаётся и имеет manifest с checksum.
- `db.py` поставляет `tests/fixtures/admission.py` — общий конструктор строки наблюдения и общий список `(canonical, admission_reason)` для всех тестовых случаев, включая unknown-время, истёкшую строку и blocked. Без этой фикстуры семнадцать модулей напишут свои тестовые данные и разойдутся.

Правила совместимости между модулями:

- Модуль **не создаёт** вторую БД, второй сетевой загрузчик, второй нормализатор прокси и второй worker-протокол. Точка нормализации и сетевого входа — `proxytool.py` (интегратор подключает).
- Модуль **не пишет DDL**. Единственный инструмент — `db.migrate()`; право писать DDL в `open_db` есть только у интегратора.

- Модуль, которому нужна правка чужого файла, описывает её в handoff и **не ждёт**: продолжает делать всё независимое, включая тесты на mocks и фикстурах.

### 2.3 Что в сценарии нужно поправить, чтобы волны состоялись

Сценарий на `:665-666` запускает `BUILDS.map(...)` одним `Promise.all`, то есть все 18 модулей, включая `db` (`:347`), стартуют одновременно. Пока это так, первая волна существует только на бумаге: к моменту, когда `db.py` будет готов, остальные семнадцать уже закончат писать против выдуманной схемы. Первый полный прогон (`:704`) только печатает код выхода и ничего не блокирует, поэтому расхождение схем обнаружится уже после того, как восемнадцать представлений лягут в дерево. **Правка сценария обязательна до запуска:** `db` выносится из `BUILDS` в отдельный предварительный `await`, остальные запускаются после его завершения. Это единственное место, где мой документ требует изменения самого workflow, и оно не может быть выполнено мной — файл сценария принадлежит владельцу прогона.

## 4. Формат handoff

Каждый файл `docs/integration/HANDOFF/<имя>.md` — это запрос на изменение чужого файла, а не отчёт о работе. Обязательные поля:

```
# Handoff: <имя>

**Требования:** F.., дефект ..
**Контракт:** CONTRACTS.ru.md §.. (версия 1)
**База:** ревизия, на которой писался модуль

## 1. Прошу внести в <чужой файл>
- <файл>:<строка или функция>
- что именно заменить/добавить (конкретный вызов, сигнатура, тип)
- почему именно здесь (контрактная ссылка)

## 2. Что уже сделано у меня
- публичный API моего модуля, на который это опирается
- имя функции, которую надо вызвать, её аргументы и что она возвращает

## 3. Совместимость
- что ломается, если не внести (конкретный сценарий)
- что НЕ ломается: обратная совместимость, legacy-данные, существующие тесты

## 4. Проверки
- точная команда и её результат
- что осталось непрочитанным

## 5. Открытые вопросы
```

Handoff без пунктов 1 и 4 — не handoff. Handoff, который переписывает чужой модуль целиком, отклоняется: он нарушает правило одного writer и означает, что границу модулей надо проверить заново.

## 5. Запрещённые зоны

- `/Users/main/Desktop/111/proxy-workbench-sources` — отдельная рабочая копия чужого workflow. **Ни одного файла там не редактируется**, только чтение. `sourcedesk.py` готовит контракт приёмки, а не переписывает чужую работу.
- `proxy_workbench/ui/**` как дизайн: нельзя запускать общий редизайн, менять темы, layout, визуальный язык или переписывать существующие сценарии ради эстетики (MASTER-PROMPT §0).
- Полный `unittest discover -s tests` **не запускается исполнителями**: каждый гоняет только свой участок командой `.venv/bin/python -m unittest tests.test_<модуль>`. Кто и когда запускает полный набор — см. §5.1; в первой редакции этого документа было написано «один раз интегратор», и это было неверно.
- `git reset --hard`, `git clean`, `git stash`, `checkout` по всему дереву не выполняются. Только адресные операции со своими файлами.
- Секреты: никаких настоящих паролей, токенов и учётных данных. Canary-секреты в тестах обязаны отсутствовать в БД, логах, `argv`, обычных файлах и JSON.
- Никаких массовых проверок публичных прокси, DNSBL и сторонних сервисов. Доказательства — локальные контролируемые сценарии, моки и фикстуры.

### 5.1 Кто запускает полный набор тестов

Проверено по сценарию: `.venv/bin/python -m unittest discover -s tests` выполняется **пять раз, из них три безусловно и два условно**.

| Прогон | Строка сценария | Условность | Кто отвечает за красный результат |
| --- | --- | --- | --- |
| `foundationGate` | `:704` | безусловно, сразу после волны BUILDS | На момент прогона код ещё не полный; красный здесь ожидаем и **не является ошибкой исполнителя** |
| `integratedGate` | `:884` | безусловно, после интеграции | Интегратор |
| `retryGate` | `:898` | условно, в цикле дочистки | Интегратор |
| `postFix` | `:1057` | условно, после правок ревьюеров | Автор исправления, на чьём диффе нашли |
| `finalGate` | `:1067` | безусловно, финальный | Приёмка (`:1078`) |

`foundationGate` на `:704` только печатает код выхода (`log(... foundationGate.exitCode)`) и ничего не блокирует. Практический вывод для исполнителя: **красный полный прогон после волны модулей — не твоя ошибка и не повод править чужие файлы**, чтобы «помочь». Свой участок ты доказываешь своей командой из §2 и записываешь её в handoff. Дополнительно выполняется `packaging/smoke.py` (`:904` и `:1072`).

## 6. Разрешение конфликтов

1. Конфликт по содержанию — не по строкам. Два исполнителя хотят разного поведения: решение принимает владелец контракта (интегратор) на основании `CONTRACTS.ru.md`, и результат пишется туда же.
2. Конфликт по владению файлом: handoff отправляется владельцу файла. Если владелец не отвечает, изменение не применяется — файл остаётся в последнем согласованном состоянии. Молчаливое «кто быстрее нажал commit» не является разрешением.
3. Конфликт схемы: версия схемы и порядок миграций определены в `CONTRACTS.ru.md` §3.3 и реализуются **исполняемым** мигратором в `db.py`. Модуль, которому нужна новая колонка или таблица, приходит в handoff с требованием и номером целевой миграции и **не пишет DDL**. Две параллельные версии схемы — самая дорогая ошибка этого этапа, потому что она обнаруживается только на полном прогоне тестов; поэтому миграции вынесены в отдельную первую волну (§2.1).
4. Изменение общего контракта обсуждается с непосредственными потребителями и отражается в их проверках **до** интеграции. Не требуется общий совет всех исполнителей по каждому локальному изменению — достаточно, чтобы потребитель нового имени поля или нового кода ошибки обновил свои тесты.
5. Индекс git может быть занят: при `index.lock` — подождать и повторить один раз; если не вышло, оставить файлы незакоммиченными, интегратор соберёт их сам.

## 7. Как интегратор это применяет

Порядок интеграции, который следует из владения выше:

1. Прочитать `CONTRACTS.ru.md`, этот файл и все файлы в `docs/integration/HANDOFF/`.
2. Убедиться, что `db.py` закончен и его шесть обязательных тестов (CONTRACTS §HANDOFF 2.1) зелёные. Если нет — вернуть волну 2 на доработку, а не подключать модули к неготовому мигратору.
3. Подключить модули к существующему движку: сканирование, хранение, отбор по свежести, экспорт, задания, пулы, профили, коллекции, импорт, источники, ключи, API должны **использовать** их, а не дублировать логику рядом. Обходные пути, обходящие контракт, удаляются или делаются тонкими.
4. Применить точечные патчи из handoff по таблице §1.5. Патч, который переписывает чужой модуль, отклоняется и возвращается автору.
5. Закрыть дефекты, живущие в его собственных строках: 1, 2, 4, 6, 7, 8, 9, 20.
6. Собрать `/v1` с compatibility path для legacy read-only токена — без расширения его прав.
7. Согласовать error codes, единицы, permissions и policy между CLI, GUI и API; добиться равенства составов по §2.3 CONTRACTS, проверяемого `tests.test_parity`.
8. Создать `tests/test_acceptance.py` по сквозным сценариям из MASTER-PROMPT §7.
9. Передать результат четырём независимым ревьюерам (CONTRACTS §7.4) и дождаться их вердикта; автор участка не принимает себя.
10. Запустить `.venv/bin/python -m unittest discover -s tests` и `.venv/bin/python packaging/smoke.py .venv/bin/proxy-workbench` на интегрированной ревизии.
