# Карточки принятых функций

Все F01–F28 приняты в **дорожную карту**, а не одновременно в ближайший релиз. У каждой карточки минимальный законченный объём; расширения из каталога не разрешают автоматически увеличивать его. Частота использования — гипотеза по сценарию, а не измеренная статистика. Текущее состояние сверяется по [матрице](02-capability-matrix.ru.md) и [аудиту](evidence/audit-code.md).

P0 — основа следующего функционального релиза; P1 — следующий необходимый уровень полезности; P2 — после проверки спроса/основы. Это продуктовый порядок, не классификация уязвимостей. Сложность: S — локальное изменение; M — несколько согласованных компонентов; L — новая модель/миграция; XL — несколько подсистем и платформ. Оценки относительные, без обещаний сроков.

## F01. Явные режимы проверки и базовая передача без ручного URL

**Проблема, аудитория, частота.** Новичку при каждом запуске нужен работающий прокси, а не обязанность придумать target; разработчику иногда нужна дешёвая диагностика порта/протокола.

**Сценарий и обход сейчас.** Выбрать «обычные рабочие», N=5 → получить проверенные на встроенном профиле записи. Сейчас есть default example.com, collect и TCP-prefilter; пользователь должен понимать скрытый смысл этих механизмов.

**Текущее состояние.** Частично: `target_config`, `reachable`, `collect` реализованы; независимой модели уровня доказательства нет. Сервисные HTTP probes уже существуют.

**Поведение.** Явные collect, TCP, handshake, basic, service/custom, recheck; мониторинг — режим задания/пула. Basic отдельно сообщает HTTP и HTTPS capabilities, проверенный target и дату. Успех TCP не называется «рабочий прокси».

**Минимальный законченный объём.** Общая схема режима, выбор в GUI/CLI/API, именованный basic-профиль, отдельные TCP/handshake результаты, понятные labels. Начальный HTTP(S) probe использует документированный доступный контракт; его оператор/лимиты проверяются до обещания массовой эксплуатации. Ни новый произвольный публичный endpoint, ни ручной URL не навязываются молча.

**UI/backend/данные.** Переключатель цели вместо длинной формы; dispatcher существующих операций; probe_kind/capabilities/version в результате. Backend переиспользует существующий checker.

**Зависимости.** F05 — версия профиля; F09 — тип доказательства; поддерживаемый probe contract. Для первой версии возможна совместимость с текущим hash профиля.

**Риски.** Недоступность контрольного сайта, нагрузка, ложный успех captive portal. До решения endpoint governance нельзя объявлять basic production-ready. [IANA](https://www.iana.org/help/example-domains).

**Приёмка.** TCP-only mock никогда не появляется в basic-пуле; basic без ввода URL проходит локальный HTTPS mock с проверкой содержимого; неверный сертификат не даёт успех; у collect нет искусственного `passed`; GUI/CLI дают одинаковые probe-kind и вердикты.

**Сложность / приоритет / почему.** M–L / P1, функциональная основа. Ясный смысл проверки полезнее новых логотипов в каталоге; но R1 может использовать существующие явно подписанные targets.

## F02. Изолированные коллекции и принадлежность нескольким спискам

**Проблема, аудитория, частота.** Владелец собственных прокси и нескольких проектов использует списки регулярно. Публичные адреса не должны попадать в результат проверки собственного файла.

**Сценарий и обход сейчас.** Создать «Проект А», импортировать файл, проверить только его. Сейчас кандидаты общие; обход — отдельные `--data` каталоги, с неудобным переключением GUI и дублированием данных.

**Текущее состояние.** Отсутствует полноценная collection-модель: общие `candidates`, `results(profile,proxy)`; отключение источников прекращает новый сбор, но не очищает область scan.

**Поведение.** Выбранная коллекция задаёт scope импорта, задания, фильтра, выдачи и экспорта. Один доступ к endpoint может принадлежать нескольким коллекциям. «Публичные» и «Мои» — отдельные коллекции; смешивание только явно.

**Минимальный законченный объём.** Создать/переименовать/архивировать, добавить/удалить членство, выбрать scope проверки и экспорта; миграция старой базы в «Ранее собранные». Без командных workspace и облачных аккаунтов.

**UI/backend/данные.** Список коллекций + count, selector в запуске/результатах; collection/membership таблицы и обязательный scope в job context; стабильные IDs. Выбор последнего профиля перестаёт неявно менять чужую коллекцию.

**Зависимости.** Нет продуктовых предпосылок; версия схемы и миграция с восстановлением pre-migration snapshot обязательны. F04 расширяет member identity credential reference.

**Риски.** Ошибочная реконструкция private/public provenance старых записей; удаление общего endpoint при удалении membership; разные пароли одного адреса.

**Приёмка.** После публичного сбора импорт двух собственных адресов проверяет и экспортирует ровно выбранные два; общий member остаётся в B после удаления из A; CLI/GUI/API одинаково применяют scope; rollback восстанавливает pre-migration snapshot и отдельно сохраняет новую БД; старый binary не пишет в новую schema; старые данные не получают выдуманной метки «свои».

**Сложность / приоритет / почему.** L / P0, обязательная основа. Это предпосылка авторизованных списков, отдельных пулов и честного сравнения; важнее массовых визуальных операций.

## F03. Транзакционный импорт с preview и merge/replace

**Проблема, аудитория, частота.** Любой пользователь при добавлении списка хочет увидеть, что принято, потеряно и заменено.

**Сценарий и обход сейчас.** Перетащить файл/вставить текст → увидеть распознанные, дубликаты и ошибки → выбрать коллекцию и commit. Сейчас есть textarea, загрузка файла и `--input`, но нет полноценного безопасного diff импорта.

**Текущее состояние.** Частично; parsing, dedup, auto protocol уже есть. UI меняется параллельно — перепроверить новый import/test UI.

**Поведение.** TXT/URI и CSV с сопоставлением колонок; предпросмотр строк, явная схема, ошибки по номеру строки, редактирование неоднозначности. Merge добавляет членство; replace заменяет только выбранный список.

**Минимальный законченный объём.** File + clipboard + preview + TXT/URI + commit/отмена + merge/replace + отчёт. CSV mapping — последующее расширение этой карточки; URL/subscription вынесены в F27, универсальные YAML/JSON адаптеры в F13.

**UI/backend/данные.** Мастер из выбора входа, preview и подтверждённого diff; parser отдаёт normalized item/reason; import_batch и секрет-свободная provenance (line ID/очищенные поля), транзакция membership с collection revision. Полные секретные строки не сохраняются ни в settings/gui-input, ни в БД/логах. Secret staging согласуется с DB commit через compensation/reconciliation.

**Зависимости.** F02; F04 для hostname/auth. Ограничения размеров и обработка encoding.

**Риски.** UTF-8 BOM, CRLF, IPv6 colons, `%40` в пароле, повторы, смешанные протоколы, повреждённые CSV. Preview не должен менять БД.

**Приёмка.** Фикстура с 10 valid, 2 duplicates, 3 invalid возвращает согласованные счётчики и номера ошибок; отмена не меняет membership; прерванный commit не оставляет половину replace; повтор одного commit не дублирует access; устаревший preview требует повторного diff; для R1 commit в активно проверяемую коллекцию откладывается; credential variants не сливаются; секреты маскируются.

**Сложность / приоритет / почему.** M–L / P0, основа. Полезнее добавления десятков редких форматов без объяснения ошибок.

## F04. Собственные hostname-прокси с авторизацией

**Проблема, аудитория, частота.** Пользователь платного/собственного поставщика нуждается в этом при каждом подключении. Популярный для таких списков формат сейчас не проходит normalizer.

**Сценарий и обход сейчас.** Добавить hostname:port, username/password → проверить → использовать через gateway или явно экспортировать в поддерживаемый клиент. Сейчас такие прокси приходится проверять отдельным инструментом.

**Текущее состояние.** Отсутствует end-to-end: `normalize` отклоняет hostname, userinfo и private IP. `--allow-private-sources` относится к серверу списка, не к proxy endpoint. HTTPX способен передать auth, но это лишь нижний транспорт. [HTTPX](https://www.python-httpx.org/advanced/proxies/).

**Поведение.** HTTP Basic proxy auth и SOCKS5 user/password; hostname как стабильная идентичность; secret reference; credentials никогда не уходят target как его Authorization. DNS-ошибка, auth-required, auth-failed и locked-vault различимы. Private endpoints — последующее расширение с отдельным явным режимом собственной коллекции, вне R1. В R1 hostname перед соединением проверяется по разрешённым фактическим IP, включая все DNS fallback; защита public-source fetch не ослабляется.

**Минимальный законченный объём.** Import → OS secret storage/сеансовый ввод → проверка → local gateway → поддерживаемый экспорт с явным выбором включения secrets. Два аккаунта одного сервера различаются. R1 поддерживает local gateway и один выбранный прямой внешний формат; остальные новые access types явно unsupported. NTLM/Kerberos, private endpoints, автоматическая покупка и provider APIs вне MVP.

**UI/backend/данные.** Поля host/port/protocol/auth, скрытый пароль, замена credential; endpoint/access/secret_ref + access_revision; rotation/rebind/revoke инвалидируют admission до новой проверки. Normalizer, resolver, transports, gateway, API redaction и format serializers согласованы. CLI не требует пароль в argv; отдельный worker получает секрет через OS adapter/ограниченный локальный IPC, а не plaintext файл. Сеансовый ref живёт в конкретном process/broker lifetime; отдельно запущенный consumer запрашивает новый ввод либо secret_unavailable.

**Зависимости.** F02/F03; OS vault abstraction; capability matrix F28. В headless/portable отсутствие vault ведёт к сеансовому вводу, не plaintext fallback.

**Риски.** Утечки через SQLite, URL, subprocess args, exception, clipboards, backup; hostname меняет IP; auth относится к hop; proxy provider session username не просто ярлык. Не обещать SOCKS4 password auth.

**Приёмка.** Локальные auth mocks проходят путь import/check/gateway; неверный пароль даёт auth-failed; в обычном JSON/logs/support bundle и managed data/input-файлах нет секретов (явно заказанный внешний secret export — отдельное исключение); две credential refs независимы; locked vault объяснён; hostname не схлопывается с IP; DNS→private fallback блокируется до auth; новый пароль не наследует pass; vault/DB commit failure восстанавливается без orphan ready access; неподдерживаемый экспорт отклоняется с причиной.

**Сложность / приоритет / почему.** L–XL / P0, основа. Открывает ранее недоступный класс пользователей и снижает зависимость от публичных списков; полезнее новых неиспользуемых протоколов.

## F05. Именованные версии профилей и правила all/any/K

**Проблема, аудитория, частота.** Разработчик повторяет одинаковые проверки между проектами; power user использует наборы сервисов регулярно.

**Сценарий и обход сейчас.** «API проекта» с двумя обязательными проверками и минимум одной из двух дополнительных. Сейчас можно сохранять JSON config/settings; все targets должны пройти, в GUI используется последний профиль.

**Текущее состояние.** Частично: hash профилей и один общий threshold, применяемый к каждому target, уже есть; именованной библиотеки и агрегатора any/K не найдено.

**Поведение.** Профиль сохраняется под именем, имеет immutable revision. Обязательные probes всегда обязательны; optional set имеет явное all/any/K/none. Можно клонировать пресет, сравнить изменение и переключить историю.

**Минимальный законченный объём.** CRUD/clone профиля, версионирование, выбор ревизии, агрегатор для HTTP probes и dry-run валидатор. Поддержка новых probe engines — F20.

**UI/backend/данные.** Библиотека в разделе проверок; backend вычисляет общий verdict; profile_id/revision/digest; selection и measurement settings разделены, но их связь явно фиксируется в job.

**Зависимости.** F09; совместимая миграция существующих hash configs. Не нужен отдельный daemon до библиотеки профилей.

**Риски.** Изменение fail-fast может исказить знаменатель; пустой optional any/K, недостижимый K; случайное переиспользование несовместимых наблюдений.

**Приёмка.** Таблица истинности для mandatory+all/any/K соблюдается; unknown mandatory не проходит; K>size, K≤0, any(empty) и zero-effective-probe admission отвергаются; предыдущая ревизия и её результаты читаются; одинаковый config даёт одинаковые вердикты во всех интерфейсах.

**Сложность / приоритет / почему.** M–L / P1, основа. Делает уже существующую многосервисность полезной для реальных задач; важнее расширения числа пресетов.

## F06. Поддерживаемый каталог сервисов и наборов

**Проблема, аудитория, частота.** Новичку нужна готовая проверка, сопровождающему — способ отличить устаревший preset от плохого прокси; запрос возникает регулярно.

**Сценарий и обход сейчас.** Найти сервис по названию/категории, выбрать «сайт» или «API», сохранить набор. Сейчас фиксированный массив девяти presets в JS.

**Текущее состояние.** Есть готовые HTTP presets; не добавлять их заново. Telegram homepage, Discord discovery и OpenAI expected 401 имеют узкий смысл.

**Поведение.** Категории, поиск, наборы, собственные копии, описание «что проверяется», probe type, maintainer, revision, last validated, deprecated reason. Обновление показывает diff и не переписывает собственный профиль.

**Минимальный законченный объём.** Перенести действующие presets в версионируемый data manifest, schema validation и поддерживаемые fixtures; поиск/наборы; ручное обновление без обязательного аккаунта. Никакого автоматического claim «звонки работают».

**UI/backend/данные.** Каталог и badge устаревания; общий backend reader для GUI/CLI; metadata + signatures/checksums для распространяемого пакета при наличии обновлений.

**Зависимости.** F05/F09; для реальных WS/media probes F20. Выделенный владелец и процедура ревизии.

**Риски.** 401/403/200 могут меняться; challenge page при 200; чужие rate limits. Отсутствие последней верификации отражается в UI.

**Приёмка.** Все текущие presets сохранены с точным уровнем доказательства; deprecated preset не считается fault прокси; update не меняет pinned ревизию; собственная копия переживает update; live проверки каталога выполняются только в явно разрешённом процессе, не скрыто в CI.

**Сложность / приоритет / почему.** M / P2, полезное следующее. Актуальность существующих проверок важнее числа логотипов.

## F07. Расширенные параметры и assertions

**Проблема, аудитория, частота.** Разработчику иногда нужна проверка структуры API и точной стадии отказа; обычному пользователю десятки настроек мешают.

**Сценарий и обход сейчас.** Проверить JSON `/status` по `$.ready == true` с ограниченным redirect и таймаутом чтения. Сейчас доступны GET/HEAD, статусы, contains/hash, общий/connect timeout и лимит body.

**Текущее состояние.** Частично. Полные JSON assertions, управляемые redirects, DNS policy и стадийная диагностика не являются готовыми возможностями.

**Поведение.** Простые пресеты раскрываются в advanced: connect/handshake/TLS/TTFB/read/total deadlines, attempts/interval/backoff, max body, status/content/JSON assertions, bounded redirects, TLS verification и DNS mode по capability transport.

**Минимальный законченный объём.** Типизированные JSON-path/equality/presence assertions без исполнения кода, интервалы и redirects с ограничением; stage diagnostics только для реально наблюдаемой стадии. Остальные поля включать, когда транспорт действительно умеет их обеспечить; не рисовать неработающие переключатели.

**UI/backend/данные.** Advanced editor с preview нормализованной конфигурации; общий validator; версия assertions и transport options в profile.

**Зависимости.** F05/F09; документация transport и локальный стенд DNS/TLS. Авторизация собственного target API — последующее отдельное расширение F07 с иным secret scope; в upstream-auth R1/F04 она не входит и в публичные presets не попадает.

**Риски.** ReDoS/скрипты в assertions, redirect к нежелательному адресу, разница SOCKS DNS modes, выключение TLS. Небезопасный режим маркируется и не превращается в рекомендуемый default.

**Приёмка.** HTML-капча с 200 не проходит JSON assertion; redirect loop завершён с причиной; deadline ограничивает всю пробу; неподдерживаемый DNS option отвергается; GUI/CLI применяют один config.

**Сложность / приоритет / почему.** M–L / P2, полезное следующее для разработчиков. Структурная проверка ответа ценнее безграничного скриптового DSL.

## F08. Страны, выход, ASN и честные unknown

**Проблема, аудитория, частота.** Пользователь поиска по стране делает это часто; endpoint location не всегда совпадает с местом выхода.

**Сценарий и обход сейчас.** «Германия или Нидерланды на выходе, исключить определённую сеть». Сейчас есть ISO country include, endpoint/exit display, ASN и hosting heuristic; поиск по названиям и политика неизвестного неудобны/ограничены.

**Текущее состояние.** Частично. GeoIP и ASN не создавать заново; В WIP уже найдены RU/EN country picker, multi chips и региональные наборы; их нужно переиспользовать после проверки, а не создавать повторно.

**Поведение.** RU/EN country picker; include/exclude; выбор endpoint/exit; unknown отдельно; version/age/источник геоданных; ASN/organization/CIDR фильтры, IPv4/IPv6 endpoint и destination capability раздельны.

**Минимальный законченный объём.** Именованный picker и полная семантика endpoint/exit/unknown, exclude sets, metadata версии; атомарное обновление существующих баз с сохранением последней исправной. Квоты — в F14, дорогой geo-поиск — budget-aware.

**UI/backend/данные.** Один geo selector в форме и результатах; location observations с provenance/conflict; общая selection policy. Read-only exit-фильтр ничего не измеряет: показывает unknown/исключает его согласно policy и предлагает отдельное задание. При поисковом measurement job planner назначает judge-пробу, а не отбрасывает exit-кандидата по входной стране. У hostname география привязана к наблюдённому resolved IP с датой; без разрешения имени — unknown, не строка hostname в IP-базе.

**Зависимости.** F09, judge capability F01/F20; existing DB-IP. Название ASN не служит доказательством residential/mobile.

**Риски.** Неточность/устаревание базы, rotating exit, несовпадение provider claim, ограничения загрузки данных. Требования attribution сохраняются.

**Приёмка.** Endpoint DE/exit NL проходит exit=NL и не endpoint=NL; unknown не становится «не NL» без явной политики; повреждённое обновление не стирает базу; RU/EN названия дают одни ISO; IPv6 не сливается с IPv4.

**Сложность / приоритет / почему.** M / P1, полезное следующее. Уточняет уже популярный country-сценарий; важнее глобального поиска дополнительных списков.

## F09. Свежесть, доказательства и объяснение рекомендации

**Проблема, аудитория, частота.** Все пользователи при каждом выборе должны отличать «когда-то прошёл» от «годится сейчас» и наблюдение от гипотезы.

**Сценарий и обход сейчас.** Открыть «Почему подходит» → увидеть профиль, время, 2/3 попытки, stage, страну и причины порядка. Сейчас есть samples/history counters/score, но отсутствует единая admission TTL и причинная карточка.

**Текущее состояние.** Частично; age есть как timestamp, история — в основном последний payload + counters. Редкость в списках уже влияет на recommendation, но связь с нагрузкой не доказана.

**Поведение.** Outcome отдельно от freshness: passed/failed/unknown/skipped и fresh/stale. Min evidence/sample count виден; рейтинг объясняет вклад метрик. Rarity — экспериментальный сигнал, не утверждение «прокси меньше используют». Свежий отрицательный результат не скрывается старым положительным.

**Минимальный законченный объём.** Profile/access revision/checked_at/max_age в общей выборке; current vs history; expired исключён из «рабочих» по явно заданной политике; атомарная публикация generation; explanation существующего score. Обязателен узкий non-destructive recheck с фиксированным input scope: старый результат не удаляется до нового, stale/failed можно явно выбрать для перепроверки, даже когда они не допускаются потребителю. Полная очередь F11 позже. Без ML и больших временных рядов.

**UI/backend/данные.** Freshness badge, «проверить снова», evidence drawer; общий selector GUI/API/CLI/gateway; immutable generation manifest с scope/version/time. Архив наблюдений добавляется постепенно, без переименования счётчиков в полный event log.

**Зависимости.** F02 для scope; существующие profiles; общий с F28 eligibility/publication contract. F11 позже добавит network epoch; R1 не обещает актуальность в неизвестной новой сети. Gateway binding к collection/profile/policy уже обязательна для R1.

**Риски.** Очень короткий TTL опустошает pool; очень длинный создаёт ложное доверие; часы ОС меняются. TTL измерения и жизненный цикл cache не тождественны.

**Приёмка.** Frozen-clock fixture одинаково исключает expired во всех потребителях при каждом чтении/new connect, даже без изменения generation; mixed-age rows имеют индивидуальный TTL, clock rollback/future timestamp дают uncertain; history видна; stale выбирается recheck и действительно измеряется заново; new rows не сочетаются с old status; удалённая generation больше не выдаётся gateway; unknown не рисуется 100%; малое число проб подписано.

**Сложность / приоритет / почему.** L / P0, основа. Каждая следующая автоматизация зависит от корректного понятия пригодности; важнее нового непрозрачного quality score.

## F10. Диагностика нулевой выдачи, сети и target

**Проблема, аудитория, частота.** Новичок регулярно сталкивается с «ничего не найдено»; разработчик иначе перебирает настройки вслепую.

**Сценарий и обход сейчас.** После нуля увидеть воронку: загружено → распознано → scope → geo → port → target → свежие. Сейчас есть logs/progress/errors, но нет полного объяснения и проверки общих причин.

**Текущее состояние.** Частично; transport exceptions и HTTP/content errors уже есть. Не считать каждую общую ошибку доказанной неисправностью прокси.

**Поведение.** Разделять source/network/DNS/proxy auth/TLS/target assertion/filter/budget failures. Контрольные probes: прямой доступ и известный ранее успешный путь, где это допустимо; общий outage помечает результаты inconclusive. Прямое соединение может быть само заблокировано и не является универсальным oracle.

**Минимальный законченный объём.** Воронка с reconciliation counters, топ причин, действия по каждой; health-state target/network и остановка массового ухудшения score при общем сбое. Ослабление фильтра только явным действием.

**UI/backend/данные.** Диагностическая карточка задания; stage/error codes + health observation; event «нужна сеть»; resume после восстановления.

**Зависимости.** F09, counters scheduler/collector; F11 для автоматического pause. Контрольные обращения отражаются в сетевом бюджете.

**Риски.** Direct path недоступен по иной причине; rate limit на target; слишком уверенная причинная атрибуция. Формулировка «вероятно проблема target/сети» при неполных данных.

**Приёмка.** Captive portal, down target, неверный пароль, zero parser rows и слишком строгая страна показывают разные причины; source не удаляется при target outage; counters сходятся; восстановление не требует очистки данных.

**Сложность / приоритет / почему.** M–L / P1, основа. Сокращает бесполезные повторные запуски; важнее универсального «попробуйте больше workers».

## F11. Сохраняемые задания, очередь и восстановление

**Проблема, аудитория, частота.** Любая долгая проверка переживает остановку, сон или сбой; нескольким проектам нужна очередь.

**Сценарий и обход сейчас.** Приостановить проверку, закрыть окно, продолжить с теми же scope/config. Сейчас результаты частично сохраняются, есть stop/resume по профилю и single-writer lock; это не журнал заданий.

**Текущее состояние.** Частично. При recheck старые payload удаляются до нового результата; interrupted job не равен точно восстановленному run.

**Поведение.** Persisted job states queued/running/pausing/paused/waiting_network/completed/failed/cancelled; checkpoint; один writer, ограниченная очередь, приоритет интерактивной задачи. Новая ревизия профиля создаёт новое задание.

**Минимальный законченный объём.** Одна активная проверка, несколько queued, pause/resume/cancel, сохранённый scope snapshot, причины interrupted, recovery после process death. Новое наблюдение публикуется после фиксации, не удаляет заранее прошлую историю.

**UI/backend/данные.** Раздел заданий; coordinator над существующим движком; job/input_snapshot/checkpoint/event sequence. Lease процесса не подменяется PID без проверки живости; stale lock не удаляется вслепую.

**Зависимости.** F02/F05/F09. Network epoch и переоценка freshness после sleep/смены сети; F10 помогает выявить outage.

**Риски.** Повтор пробы после crash возможен; нельзя обещать exactly-once сетевой запрос. Идемпотентна фиксация результата, а не внешний HTTP побочный эффект. Нельзя повторять mutating target requests автоматически.

**Приёмка.** Kill между probe и commit не повреждает БД; resume не удваивает счётчик observation ID; пауза сохраняет все завершённые работы; recheck DE не стирает историю NL; sleep не порождает одновременно десятки пропущенных запусков.

**Сложность / приоритет / почему.** L / P1, основа. Нужна до постоянных пулов и сложного scheduler; распределённая очередь избыточна.

## F12. Конвейер и быстрый поиск N с контролем нагрузки

**Проблема, аудитория, частота.** Все пользователи хотят ранний полезный результат, ноутбук не должен терять отзывчивость.

**Сценарий и обход сейчас.** Получить первые 5 ещё пока большой источник загружается. Сейчас `--want`, приоритет известных, prefilter, rate limit, bounded scan queue и fit_workers есть; сбор и scan запускаются последовательно.

**Текущее состояние.** Частично. Предлагать pipeline collection→check, а не заново параллельные проверки.

**Поведение.** Новые batches поступают в ограниченную очередь; дешёвый handshake перед expensive probes; известные хорошие первыми; общий budget делится между source/target/proxy. Автонагрузка реагирует на saturation, timeout spikes и 429.

**Минимальный законченный объём.** Bounded streaming collection→scan→visible results, достижение N останавливает новое планирование, сохраняет уже найденное и незавершённый input; conservative adaptive limit с ручным пределом. Без сложного оптимизатора и «максимальных workers».

**UI/backend/данные.** Первые пригодные сразу; progress по стадиям; bounded queues + batch DB writer; completion reason `goal_reached`, `budget_exhausted`, `sources_exhausted`.

**Зависимости.** F11/F09/F02; F13 stream-capable adapters. Slow source не должен задерживать первые результаты остальных.

**Риски.** Bias первых источников, лишние in-flight после N, память pending list, target rate limits, noisy benchmarks. Не обещать точный рост скорости без измерения.

**Приёмка.** На локальном slow-source стенде первый результат виден до EOF; память ограничена queue budget; после N не планируются новые probes, overshoot не больше in-flight; одинаковые критерии принятия при 8/128 workers; 429 вызывает backoff.

**Сложность / приоритет / почему.** L / P1, полезное следующее. Улучшает время до результата, тогда как повышение workers часто ухудшает его.

## F13. Управление источниками, адаптеры и происхождение

**Проблема, аудитория, частота.** Power user и сопровождающий регулярно добавляют/исправляют источники и хотят понимать их пользу.

**Сценарий и обход сейчас.** Подключить URL, посмотреть формат/образец/ошибки, обновлять дёшево, отключить временно плохой источник. Сейчас каталог, text/HTML/Geonode, source reports, update/prune уже есть.

**Текущее состояние.** Частично. Нет цельного source entity, generic adapter contract, validators cache и корректной семейной атрибуции; автоматический prune основан на контекстной метрике.

**Поведение.** Каталог с publisher/family/mirror, parser kind, access/terms, enabled/quarantined, ETag/Last-Modified, last fetch/last changed, parsing preview и new unique contribution. Сбор, работа прокси и пригодность под фильтр — разные показатели.

**Минимальный законченный объём.** Source schema поверх нынешнего каталога, preview, text/CSV/ограниченный JSON adapter, conditional fetch, retry/backoff, временный quarantine с ручным восстановлением. Без поиска нового глобального каталога в этом задании.

**UI/backend/данные.** Карточка источника и отчёт; adapter interface с size/page/time budgets; source_fetch/import provenance; many-to-many sightings. Источник с parse failure не заменяет коллекцию пустотой.

**Зависимости.** F03/F09. Результаты отдельного исследования принимаются по контракту из roadmap, без автоматического доверия.

**Риски.** URL secrets, несовпадение контента, stale cached list, зеркала, пагинация, смена формата. Произвольный исполняемый plugin parser не нужен в MVP.

**Приёмка.** 304 не считается новой свежестью проверки прокси; mirror не удваивает unique contribution; bad JSON сохраняет последнюю исправную выборку с stale label; budget ограничивает pagination; source outage и target outage различаются.

**Сложность / приоритет / почему.** M–L / P2, полезное следующее. Управляемость каталога ценнее механического увеличения числа URL.

## F14. Постоянный пул с пополнением, резервом и повторным допуском

**Проблема, аудитория, частота.** Скрипту или постоянно подключённой программе нужен рабочий набор весь день.

**Сценарий и обход сейчас.** «Держать N=20 для профиля API, резерв 5, только мои коллекции». Сейчас `--watch` перепроверяет survivors, пользователь вручную собирает и запускает снова.

**Текущее состояние.** Отсутствует контроллер desired-state. Gateway уже имеет собственный in-memory cooldown/limits, но он не занимается проверками и пополнением.

**Поведение.** Цель N, минимум и reserve; перепроверка по freshness; refill из резерва/известных/разрешённых источников; cooldown→probation→admission; country/ASN quota policy; общий бюджет. Candidate rejected не удаляется навсегда.

**Минимальный законченный объём.** Один пул с N+reserve, collection scope, profile revision, max_age, refill budget, cooldown, backoff, объяснённый zero/degraded state; несколько пулов используют тот же механизм. Квоты начать с стран endpoint или подтверждённого exit, без выдуманной уникальности.

**UI/backend/данные.** Карточка «готово/нужно/резерв/дефицит»; reconciler, admission selector, persisted pool/member state и generation. Job для каждого refill/recheck связан с причиной запуска.

**Зависимости.** F02/F05/F09/F10/F11; встроенные hard request/byte/concurrency limits обязательны уже здесь; F15 добавляет расписания/OS policies и не является предпосылкой; F16 consumes. Первое пополнение может брать локальных pending, не требует завершённого нового исследования источников.

**Риски.** Невозможность N при недостатке пригодных, гонки нескольких пулов, лишние расходы, неоднозначный uniqueness по exit. Budget считает source/probe/retry/judge/speedtest payload, а не relay и не точный billable traffic; остаточный in-flight ограничен и показывается отдельно. Пул — целевое состояние, не гарантия SLA.

**Приёмка.** При N=5 и двух отказах локальные кандидаты пополняют до 5; при отсутствии кандидатов остаётся явный 3/5 без ослабления страны; cooldown восстановившегося даёт повторный допуск; budget=0 прекращает refill; private pool не получает public members; пустой пул не даёт DIRECT.

**Сложность / приоритет / почему.** XL / P1, следующий главный функциональный этап. Это существеннее «ещё один таймер recheck», но зависит от корректной основы.

## F15. Расписания, бюджеты и уведомления по изменениям

**Проблема, аудитория, частота.** Пользователь фонового пула хочет ограничить батарею, трафик и число уведомлений; ежедневно.

**Сценарий и обход сейчас.** Перепроверять рабочими часами, на мобильной сети только дешёвые пробы, сообщать при падении ниже минимума. Сейчас watch — фиксированный интервал.

**Текущее состояние.** Частично interval/rate; расписаний, общего byte/probe budget и локальных правил уведомления нет.

**Поведение.** Daily windows/interval с timezone, quiet hours, requests/bytes/concurrency budget, no-catchup после сна; pause on battery/metered network где ОС предоставляет достоверный сигнал. Notifications — только смена состояния/нужное действие, с hysteresis.

**Минимальный законченный объём.** Interval+окно, общий request/byte limit, пауза/возобновление, in-app/local OS alerts ниже minimum и при восстановлении. Webhooks/email не включены по умолчанию.

**UI/backend/данные.** Простые «экономно/обычно» и advanced budgets; scheduler поверх job coordinator; persisted counters/reset rules и notification dedup.

**Зависимости.** F11; для pool schedules — F14, для OS notifications — optional adapter F22. In-app schedules/alerts работают без tray; F20 expensive probes учитывают те же budgets.

**Риски.** DST/смена часов, недоступные network-cost APIs, частые колебания. Unknown metered state объясняется и имеет conservative user policy.

**Приёмка.** DST не дублирует job; sleep объединяет просроченные работы; byte cap прекращает большие загрузки; десять одинаковых degraded наблюдений дают одно уведомление; восстановление даёт второе; отключённые уведомления не отправляются наружу.

**Сложность / приоритет / почему.** M–L / P2, полезное следующее. Важнее сложного cron editor и внешних push-сервисов для первой версии.

## F16. Gateway для выбранных пулов и честные сессии

**Проблема, аудитория, частота.** Пользователь подключённого приложения постоянно зависит от правильного upstream и поведения отказов.

**Сценарий и обход сейчас.** Приложение А использует пул A; сессия сохраняет upstream или явно обрывается. Сейчас есть один gateway, rotation, username filters, sticky, cooldown, limits и status.

**Текущее состояние.** Частично. Повторно создавать gateway не нужно. Current sticky может сменить endpoint, а HTTPS upstream исключается.

**Поведение.** Connection config привязан к pool ID/generation; strict/failover session policy; TTL admission; лимиты по upstream/client/task; событие смены upstream. Маршрутизация начинается с отдельных локальных ports/profile bindings, без универсального rule engine.

**Минимальный законченный объём.** Выбор именованного пула, проверка freshness, strict/failover, понятные pool-empty/no-compatible-upstream/limit ошибки; read-only stats и встроенный тест подключения. Уже установленные туннели не мигрируют.

**UI/backend/данные.** Карточка подключения; Pool interface читает published immutable generation; session содержит pool/profile/access ID, политику и причину завершения; role auth отдельно от username-routing.

**Зависимости.** F09/F14/F18; F04 для auth upstream. Минимальная стабильная scope/profile/policy binding обязательна в R1 для F04/F28 ещё до полного F14; именованные пулы и strict/failover добавляются затем.

**Риски.** Strict не удерживает exit у rotating supplier; retry после передачи application bytes может продублировать операцию; неподдерживаемые протоколы теряются тихо.

**Приёмка.** Strict при потере upstream возвращает session-lost, failover создаёт event; после удаления export старые members недоступны; exhausted connection limit отличим от empty; auth не попадает target; supported/unsupported upstream видны до подключения.

**Сложность / приоритет / почему.** L / P1, полезное следующее. Предсказуемая политика полезнее обещания «один IP навсегда».

## F17. Мастер подключения браузера, приложения и скрипта

**Проблема, аудитория, частота.** Для новичка результат бесполезен без понятного последнего шага; нужен при первом запуске и смене клиента.

**Сценарий и обход сейчас.** Выбрать Firefox/приложение/curl → получить адрес, поля и проверку → увидеть, как отключить. Сейчас есть адрес gateway, API и Telegram button, файлы PAC/Clash/sing-box.

**Текущее состояние.** Существует, но разрозненно; GUI меняется. Не выдавать существующие форматы и Telegram integration за новое.

**Поведение.** Capability-aware инструкции, копирование fields, локальный тест control route, отдельно подтверждение реального client request, ссылка на профиль/пул, текущий выход где измерен, объяснение DNS/UDP ограничений. Настройки системы автоматически не меняются.

**Минимальный законченный объём.** Один хорошо проверенный browser path + generic app fields + curl/Python snippets + test + disconnect instructions. Проверка самим Workbench доказывает маршрут gateway; отметка «клиент подключён» появляется только после запроса выбранного клиента, а не автоматически. Если позже добавляется автоматическая настройка, сначала snapshot и restore предыдущих параметров.

**UI/backend/данные.** «Подключить» из списка; renderer connection recipes и diagnostic job; connector capability/version metadata. Secrets в copy требуют явного действия.

**Зависимости.** F09/F28 и действующий gateway; F16 улучшит pool routing, но не нужен для инструкции к статической выборке.

**Риски.** Различия ОС/браузеров, системный proxy не влияет на все приложения; Telegram button на другом устройстве не делает loopback доступным.

**Приёмка.** Новый пользователь на Windows/macOS завершает выбранный контрольный путь по инструкции; ошибка порта/пустого пула различима; шаг отключения восстанавливает настройки, если они менялись; инструкция не обещает весь трафик/звонки.

**Сложность / приоритет / почему.** M / P1, удобство с прямой функциональной ценностью. Проверенный путь подключения полезнее расширения ради кнопки on/off.

## F18. Общие операции GUI/CLI/API и автоматизация заданий

**Проблема, аудитория, частота.** Разработчик ежедневно автоматизирует те же действия, которые проверяет в GUI.

**Сценарий и обход сейчас.** Импортировать, запустить job, следить, получить нужную collection/profile generation. Сейчас read-only API/get уже есть, управляющие GUI routes имеют другой контракт.

**Текущее состояние.** Частично. `serve`, `get`, `test`, filters/token есть; публичных jobs/events/scoped profile operations нет.

**Поведение.** Один application layer. Предлагаемые commands: collection import, profile validate, job submit/pause/resume, pool get; JSON/NDJSON, stable error codes, schema version, cursor pagination, job events с sequence; scoped local tokens.

**Минимальный законченный объём.** Сначала общий selector/schema и CLI JSON parity; затем local-only job API поверх одной очереди, idempotency keys и polling/events. Удалённый multi-user control отдельно экспериментален.

**UI/backend/данные.** UI использует те же validated operations; adapters к CLI/HTTP; job/event/token metadata. Токены чтения результатов не дают менять jobs и читать secrets. Legacy endpoints сохраняются с documented defaults.

**Зависимости.** F02/F05/F09/F11. R1 использует существующие get/test/API с новым явным scope, без реализации всего job API.

**Риски.** Два источника истины, CLI stdout с human logs, неограниченная pagination, query-string token leakage, повтор mutation после timeout.

**Приёмка.** Один fixture выдаёт одинаковые IDs/verdict/order во всех интерфейсах; JSON stdout валиден, logs в stderr; повтор submit c тем же key возвращает тот же job; readonly token не mutates; reconnect event stream явно сообщает gap при retention.

**Сложность / приоритет / почему.** L / P1, полезное следующее. Согласованность важнее отдельного API-фреймворка или SDK на пяти языках.

## F19. Избранное, теги, заметки и массовые операции

**Проблема, аудитория, частота.** Пользователь нескольких списков каждый день выбирает поднаборы и запоминает причины исключений.

**Сценарий и обход сейчас.** Отметить 12 строк, перенести членство, временно исключить на час, сохранить фильтр. Сейчас есть поиск, сортировки, фильтры, copy page и denylist; новый UI может добавлять row actions.

**Текущее состояние.** Неудобно/частично; row test/denylist — WIP, перепроверить. Теги, избранное и saved views не подтверждены.

**Поведение.** Выделение явно «страница» либо «все найденные», tags/notes/favourite, saved filters/columns, timed exclusion и журнал изменений. Избранное не отменяет freshness и отказ.

**Минимальный законченный объём.** Selection+tags/favourite+notes+saved view+temporary exclusion; move/copy membership и undo ограниченного действия. Без сложного канбана и иерархии папок.

**UI/backend/данные.** Row actions/bulk bar; versioned filter definition; membership metadata и exclusion reason/until. Notes принадлежат collection membership, общие технические факты — endpoint/observation.

**Зависимости.** F02/F09/F18 common operations.

**Риски.** Случайная операция по всему filtered set; IP denylist блокирует другие порты; приватные заметки попадают в export. Scope подтверждается понятным count.

**Приёмка.** Bulk по 50 visible не затрагивает 500 остальных; timed exclusion истекает, но не делает failed proxy fresh; endpoint/IP/CIDR запреты различимы; saved filter одинаково воспроизводится в CLI; undo не меняет другую коллекцию.

**Сложность / приоритет / почему.** M / P2, удобство. Делать после изоляции списков; декоративные колонки без действий менее ценны.

## F20. Отдельные WebSocket, медиа, скорость и устойчивость

**Проблема, аудитория, частота.** Разработчик realtime/media и power user периодически проверяют свойства, которых HTTP status недостаточно.

**Сценарий и обход сейчас.** API доступен, но WS обрывается через 40 секунд; пользователь хочет увидеть эту разницу. Сейчас download speed, repeated attempts и jitter уже есть; реальные WS/media/session probes отсутствуют.

**Текущее состояние.** Частично. `YouTube generate_204` не проверяет видео; Discord discovery не WS; Telegram homepage не MTProto/voice.

**Поведение.** Отдельные probe types: HTTP/API; WS handshake+ping/pong+bounded duration; media manifest+ограниченный segment; sustained connection; download/upload throughput только при специальном endpoint. Метрики не сводятся в общую зелёную «совместимость».

**Минимальный законченный объём.** Сначала свой WS echo и фиксированная bounded длительность, затем медиа на разрешённом тестовом asset; существующий speedtest получает bytes/duration/context. Для каждого engine отдельный admission facet. Public accounts/DRM/голос не автоматизируются.

**UI/backend/данные.** Probe type selector и estimate traffic; engine registry с capability schema; отдельные latency/throughput/disconnect observation fields.

**Зависимости.** F05/F07/F09/F15; self-hosted endpoint protocol. WebSocket support pinned transport нужно подтвердить до реализации.

**Риски.** Дорого, нагрузка на targets, кеш и burst искажают скорость, active probes не моделируют пользовательскую сессию полностью. «Стабилен 60 секунд» не равно стабильности сутки.

**Приёмка.** Mock HTTP-ok/WS-fail разделяется; ping timeout имеет причину; media не скачивается сверх cap; Mbps сопровождается байтами и длительностью; cancelled probe помечен unknown/skipped; results не обещают UDP.

**Сложность / приоритет / почему.** L–XL / P2, продвинутое развитие. Запускать engines по подтверждённым сценариям, а не ради длинного каталога протоколов.

## F21. Честное сравнение источников и поставщиков

**Проблема, аудитория, частота.** Power user выбирает источник/поставщика еженедельно или перед продлением и хочет оценить полезный вклад, а не рекламу.

**Сценарий и обход сейчас.** Сравнить A/B под одним профилем за одинаковое окно; учитывать уникальные прошедшие, устойчивость и расходы. Сейчас source_quality и rarity уже есть, но первый источник и export filters искажают сравнение.

**Текущее состояние.** Частично; отсутствует сопоставимый benchmark с provenance и uncertainty.

**Поведение.** Раздельно fetch health, parser yield, overlap, unique tested, admission rate, survival, bytes per admitted; sample size и coverage. Supplier cost вводится пользователем, единицы тарифа показаны; никаких выдуманных цен.

**Минимальный законченный объём.** Отчёт по двум+ спискам при одинаковом profile revision, времени, budget и scope; совпадения credit каждой source family, marginal contribution отдельно. Без автоматического выбора тарифа и встроенного billing.

**UI/backend/данные.** Таблица сравнения с пояснениями bias; observation/provenance aggregation; сравнение endpoint или подтверждённых exit явно выбирается.

**Зависимости.** F02/F09/F13; F15 для одинакового budget. Separate source research даёт metadata, не заменяет локальные измерения.

**Риски.** Early-stop N, порядок источников, маленькая выборка, разная страна, общий provider network искажает вывод. «Недостаточно данных» — допустимый результат.

**Приёмка.** Перестановка A/B не меняет unique counts; shared адрес не удваивается в union; изменение export filter не объявляет источник мёртвым; сравнение разных profiles/time windows выдаёт предупреждение несопоставимости; значения легко пересчитать по fixture.

**Сложность / приоритет / почему.** M–L / P2, полезное следующее. Доказуемый вклад лучше автоматического удаления по одному нулевому экспорту.

## F22. Фоновый режим, tray/menu bar и управление жизненным циклом

**Проблема, аудитория, частота.** Пользователь постоянного подключения каждый день закрывает окно и ожидает понятного продолжения работы.

**Сценарий и обход сейчас.** Закрыть окно → работа продолжается по выбранной политике; tray показывает pool state; «Выйти» останавливает engine. Сейчас браузер может закрыться отдельно от server, но нет цельного desktop lifecycle.

**Текущее состояние.** Частично/отсутствует. Есть локальный сервер, subprocess, single-instance lock; tray, управляемого auto-start и OS recovery не найдено.

**Поведение.** Close window vs stop engine различаются; автозапуск opt-in; повторный запуск открывает имеющийся экземпляр; sleep/wake и смена сети запускают recovery, а не новый полный сбор. Выход сообщает о подключённых клиентах и выполняет bounded shutdown.

**Минимальный законченный объём.** Tray/menu bar с открыть/пауза/остановить/выйти, состояние заданий/пула, single instance, opt-in launch at login и sleep recovery. Engine имеет владельца lifecycle; не ставить системную привилегированную службу ради UI.

**UI/backend/данные.** Desktop host поверх общего engine/control API; OS adapters; persisted startup preference и last shutdown reason. Фон без открытого browser tab.

**Зависимости.** F11/F09 и lifecycle/OS host contract; F14 только для отображения pool state, не обязательная предпосылка. Полная поставка F23 следует за прототипом host; platform smoke matrix. macOS Keychain locked может приостановить auth jobs.

**Риски.** Orphan child, порт занят, ОС отключила auto-start, устаревшие after-wake observations, различная ОС-политика фоновых процессов.

**Приёмка.** Закрытие окна не убивает разрешённую фоновую задачу; «выйти» не оставляет listeners; повторный запуск открывает первый экземпляр; locked vault даёт actionable status; пробуждение не публикует старый pool как свежий.

**Сложность / приоритет / почему.** L–XL / P1, удобство и необходимая часть постоянной работы. Делать после durable jobs, иначе оболочка лишь прячет сбои.

## F23. Поставка Windows/macOS, отдельное окно и обновления

**Проблема, аудитория, частота.** Обычный пользователь устанавливает редко, но не пройдёт первый сценарий, если нужен Python/терминал.

**Сценарий и обход сейчас.** Скачать подходящий файл, открыть, получать понятные обновления с сохранением данных. Сейчас Windows .exe build есть; macOS source launcher требует Python; браузерный UI уже работает.

**Текущее состояние.** Windows packaging реализован в коде CI; наличие и запуск конкретного release binary здесь не проверялись. .app/.dmg и native lifecycle не найдены.

**Поведение.** Windows существующий .exe и macOS .app, архитектура указана; отдельное окно использует тот же UI; браузерный режим остаётся для headless/portable. Обновление показывает версию и изменения, проходит проверку происхождения и не затрагивает пользовательские данные.

**Минимальный законченный объём.** Собираемый macOS app, Windows build regression, корректные writable paths, offline first-start error handling; ручная проверка/загрузка релиза по явной команде. Автоматическая замена бинарника — последующий отдельный шаг после rollback design.

**UI/backend/данные.** Thin host, общий UI и engine; packaging per OS; version/channel/build metadata. Portable выбирается явно и проверяет writable path; не хранить рабочие данные внутри signed app bundle.

**Зависимости.** F22 только для background обещаний; F24 до миграций/автообновления. Signing/notarization требуют доступной инфраструктуры проекта, которую ещё надо подтвердить.

**Риски.** Gatekeeper/SmartScreen, x64/ARM различия, quarantine, read-only install folder, антивирус. Эти вопросы не считать автоматически решёнными PyInstaller.

**Приёмка.** Чистая Windows/macOS машина запускает без Python; пути с пробелами/кириллицей работают; обновление сохраняет коллекции; portable показывает отказ writable path до записи; browser/native отображают один state; неуспешная миграция восстанавливается.

**Сложность / приоритет / почему.** L–XL / P2, удобство с высоким onboarding эффектом. Отдельное окно имеет ценность для возврата, tray и lifecycle; переписывание UI на native framework не требуется.

## F24. Backup, восстановление и срок хранения

**Проблема, аудитория, частота.** Владелец списков редко переносит компьютер/обновляется, но потеря данных уничтожает накопленную ценность.

**Сценарий и обход сейчас.** Создать backup профилей/коллекций, восстановить на другом устройстве, заново связать secrets. Сейчас можно сохранять settings и копировать data вручную; это не согласованный backup.

**Текущее состояние.** Частично; paths и clear-data уже есть, полного backup/retention manager нет.

**Поведение.** Согласованный SQLite snapshot + manifest/schema/configs; секреты исключены по умолчанию; preview restore/merge conflicts; retention по observations/logs без удаления пользовательских списков; backup перед миграцией.

**Минимальный законченный объём.** Local export backup и restore в новый data path, проверка checksum/schema, credential placeholders, migration rollback. Без облачной синхронизации.

**UI/backend/данные.** Настройки хранения с объёмом и preview очистки; backup API (SQLite backup/координированный snapshot, не raw copy открытой БД); manifest version и recovery log.

**Зависимости.** F02/F04 schema; F11 coordinator для consistent snapshot. До F24 каждая миграция R1 всё равно обязана иметь техническую резервную копию; это не отдельный UI feature.

**Риски.** Перенос Keychain/DPAPI секретов между устройствами не прозрачен; backup может содержать адреса/заметки; history растёт; restore не должен запустить сеть автоматически.

**Приёмка.** Backup active job даёт целостное восстановление; missing secrets требуют rebind; несовместимая schema объяснена; corrupted backup не меняет существующую БД; retention сохраняет current evidence и коллекции; restore offline.

**Сложность / приоритет / почему.** M–L / P1, удобство/надёжность. Важнее синхронизации нескольких устройств без понятной модели конфликтов.

## F27. Подписки и обновление собственных поставщиков

**Проблема, аудитория, частота.** Пользователь собственного поставщика регулярно получает изменяющийся список по URL/API.

**Сложность / приоритет / почему.** M–L / P2, полезное следующее. Дает длительную ценность после ручного BYOP; без проверенного спроса API каждого поставщика не нужны.

## F28. Согласованные экспорты и контракты потребителей

**Проблема, аудитория, частота.** Пользователь регулярно передаёт результат другому клиенту и ожидает, что scope, credentials и ограничения сохранятся.

**Сценарий и обход сейчас.** Экспортировать свой список в нужный формат; увидеть unsupported rows, дату и условия. Сейчас TXT/CSV/JSON, protocol files, PAC/Clash/sing-box/proxychains уже есть.

**Текущее состояние.** Частично: generation publication есть, но API читает legacy files раздельно; empty Clash/sing-box делают DIRECT; serializers не рассчитаны на auth/hostname access model.

**Поведение.** Единый snapshot manifest: generation/scope/profile/checked_at/expires_at/capabilities. Format capabilities явно описаны: protocol, auth, DNS, TLS, IPv6. Unsupported item нельзя тихо упростить. Credentials включаются только отдельным действием; default export redacted или gateway-reference.

**Минимальный законченный объём.** Атомарное чтение manifest всеми consumers; scope-aware export; compatibility preview; единая empty policy без скрытого DIRECT; существующие unauth-форматы сохранены, а для новых auth/hostname accesses в R1 один прямой формат и gateway path; остальные сообщают unsupported. Test fixtures на целевые версии. Новые форматы не обязательны; отмена empty DIRECT — явно документируемое изменение поведения.

**UI/backend/данные.** Export drawer с count/unsupported/secret choice и предупреждением потери freshness в plain TXT; shared serializers/selectors; immutable generation/current pointer. Экспорт без creds не должен выглядеть как готовая credential-bearing конфигурация.

**Зависимости.** F02/F04/F09. TXT/PAC не способны обеспечить TTL самостоятельно — это явно обозначается; enforcement через живой gateway/API.

**Риски.** Отличающиеся версии внешних клиентов, stale static file, secrets в clipboard, mismatched status. Empty config либо безопасный отказ, либо явная ошибка генерации по возможностям клиента.

**Приёмка.** New rows никогда не смешиваются с old status; private scope не теряется; пустые PAC/Clash/sing-box не выбирают DIRECT; auth/IPv6 round-trip fixtures выбранного поддерживаемого формата корректны; неподдерживаемые HTTPS upstream перечислены; после удаления publication API/gateway возвращают empty; старый TXT подписан как snapshot, без обещания автоматического TTL.

**Сложность / приоритет / почему.** L / P0, обязательная основа. Делает существующие интеграции пригодными для нового own-proxy сценария; ценнее добавления очередного формата.
