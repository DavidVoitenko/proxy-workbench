# Концепция и цельная модель Proxy Workbench

Дата: 25 сентября 2026. Это предложение развития, а не описание уже выпущенного продукта. Фактический baseline — [матрица](02-capability-matrix.ru.md); объём реализации — [карточки](04-feature-cards.ru.md).

## Краткая концепция

**Локальная рабочая среда, которая помогает получить, проверить, организовать и подключить подходящие прокси, а затем поддерживать их пригодность для конкретной задачи.** Без обязательного аккаунта. Результат всегда отвечает на четыре вопроса: для чего подходит, чем это подтверждено, когда проверено и что сделать дальше.

Ценность для обычного пользователя: «получить несколько адресов и подключить программу». Для разработчика: «воспроизводимо проверить свой список и получить результат через CLI/API». Для продвинутого пользователя: «поддерживать отдельные пулы с понятной политикой отказа и расходом ресурсов».

В проекте уже есть сильный проверяющий движок, сбор, страны, сервисы, API и gateway. Главное развитие — явная область работы, доказательства пригодности, собственные прокси и предсказуемый жизненный цикл. Пользователь не обязан знать термины endpoint, profile digest и CONNECT, чтобы завершить первый сценарий.

## Рассмотренные альтернативы

| Модель | Выигрыш | Ограничение | Решение |
|---|---|---|---|
| Одноразовый «найти и скопировать» | Самый короткий первый запуск, низкая сложность | Не решает проекты, авторизацию, старение и автоматизацию | Сохранить как быстрый вход |
| Менеджер списков и проверок | Одинаково полезен новичку и владельцу собственных прокси; постепенно расширяется | Требует области данных и понятных статусов | **Основная модель** |
| Полноценный локальный сетевой контроллер | Единое подключение множества приложений | TUN/DNS/маршрутизация/права ОС/поддержка резко расширяют продукт | Gateway оставить; VPN/TUN вынести за пределы основной дорожной карты |

Такой выбор — продуктовая гипотеза, не результат проведённых интервью. Проверка спроса описана в [реестре предположений](08-critical-synthesis.ru.md).

## Режимы и что они доказывают

| Режим | Вход | Успешный результат доказывает | Чего не доказывает |
|---|---|---|---|
| Только собрать | Набор источников/файл | Запись распознана и сохранена | Что адрес доступен или является прокси |
| Проверить порт | Список + TCP timeout | TCP-соединение с адресом установлено | Корректный протокол, аутентификацию, прохождение трафика |
| Проверить протокол | Явная/предполагаемая схема | Завершён определённый handshake, зафиксированы auth requirements | Доступность любого назначения; SOCKS greeting сам по себе недостаточен для «рабочий» |
| Базовая передача | Встроенный профиль без ручного URL | Контрольный HTTP/HTTPS запрос передан, ответ и TLS проверены по контракту | Любой сервис, видео, звонки, анонимность или будущую стабильность |
| Для сервиса/набора | Пресеты с видами проверок | Конкретные probes прошли policy данного профиля | Полную работу приложения, аккаунта, подписки, региона или UDP |
| Свой профиль | Адреса, assertions, ограничения | Заданные критерии выполнены в заданных условиях | Условия, которые пользователь не проверял |
| Перепроверка | Коллекция/выборка + версия профиля | Получено новое наблюдение; старое сохранено как история | Неограниченную длительную доступность |
| Наблюдение / поддерживать пул | N, freshness, scope, budgets | Контроллер пытается сохранять N пригодных членов и объясняет дефицит | Возможность найти N, если их нет в разрешённых источниках |

Порт и протокол — диагностические режимы, их успех не попадает в выдачу «обычные рабочие прокси». При «быстро» можно сократить число проб, но нельзя незаметно ослабить смысл результата.

Сегодня базовый CLI target уже задан по умолчанию. Его развитие: именованный, версионируемый basic-профиль; отдельные результаты HTTP forward и HTTPS tunnel; небольшой предсказуемый ответ; контроль здоровья endpoint; показ адресов проверок в справке. `example.com` нельзя считать надёжной производственной инфраструктурой: IANA прямо описывает его HTTP-сервис как best effort для документирования. Предлагаемый probe требует согласованного оператора, политики нагрузки и собственного/self-hosted варианта; отсутствие такого оператора нельзя маскировать обещанием готовности. [IANA](https://www.iana.org/help/example-domains).

## Навигация и первый экран

Основные разделы: **Обзор · Списки · Проверки · Пулы · Подключение · Источники**. Настройки, справка и диагностика — вспомогательные. «Проект» пока является сохранённым набором ссылок на список, профиль и подключение; отдельный workspace/организационный уровень в первой версии не нужен.

На пустом обзоре три действия: «Найти рабочие», «Проверить свой список», «Подключить программу». Для первого поиска достаточно количества и режима; страна и сервис необязательны. Источники по умолчанию и ожидаемые сетевые обращения видны в свёрнутой сводке. До запуска — понятный итог: «до 10 адресов, базовая HTTPS-проверка, из публичных источников, бюджет …». Не обещать время завершения без данных.

Простые настройки: режим, количество, страна/набор стран, нужный сервис, список, экономный/обычный/тщательный профиль ресурсов. Расширенные: таймауты стадий, попытки и интервалы, DNS, redirects, assertions, лимиты, freshness, quota policy. У каждой изменённой расширенной настройки есть объяснение и возврат к значению профиля. Сохранение шаблона не запускает сеть.

Из строки результата: «Копировать», «Подключить», «Перепроверить», «Почему подходит». Из подробностей доступны стадия ошибки, профиль и версия, дата, числитель/знаменатель успехов, provenance и неизвестные свойства. Интерфейс никогда не заменяет неизвестное зелёной отметкой.

## Единая предметная модель

| Сущность | Назначение и идентичность | Связи и ограничения |
|---|---|---|
| Endpoint | Протокол + нормализованный host + port; hostname хранится как имя, не заменяется DNS-ответом | Один host/IP может иметь разные порты и протоколы; это разные endpoints |
| Доступ к endpoint | Endpoint + credential reference/revision + параметры доступа поставщика | Один адрес с двумя аккаунтами не сливается в один пригодный результат; пароль не часть публичного ID |
| Наблюдаемый адрес | Endpoint IP, resolved IP или exit IP с временем и источником | Выход может меняться между соединениями; нельзя хранить как вечное свойство |
| Коллекция | Именованное членство в наборе доступов к endpoints | Many-to-many; удаление из списка не удаляет из остальных; scope обязателен в задании |
| Источник / поставщик | Откуда и на каких условиях получена запись | Source URL, publisher/family, adapter, last fetch, credentials ref раздельны |
| Профиль | Версионируемые проверки и правило принятия результата | Stable name + immutable revision/digest; изменение критериев создаёт новую ревизию |
| Задание | Одна попытка выполнить действие над зафиксированным scope | Job ID, версия профиля, inputs, budget, checkpoints, результат и причины завершения |
| Наблюдение | Результат конкретной пробы | Стадия, тип probe, время, network epoch, версия инструмента; success/fail/unknown/skipped |
| Политика отбора | Критерии над доказательствами | Freshness, страны, ASN, max latency; не должна выдавать старую проверку за новую |
| Пул | Желаемое состояние доступных members | Коллекции-источники + профиль + N/reserve/quotas + budgets + admission policy |
| Подключение | Способ передать клиенту доступ к пулу/выборке | Local gateway, export или инструкция; generation/profile/scope видимы |

Решение по секретам: ОС-хранилище (Windows credential protection/macOS Keychain), в SQLite и конфигурации только ссылка. Для portable/headless — сеансовый ввод или явно выбранное защищённое хранилище; молчаливый plaintext fallback запрещён. Секрет источника, upstream-прокси, target API и токен управления — разные назначения и области доступа.

Решение по импортам: предварительный просмотр ничего не изменяет. Commit импорта транзакционно создаёт membership и секрет-свободную provenance (batch ID, номер строки, очищенные поля). Исходные строки с credentials не сохраняются в settings, input-файлах, БД или логах. OS vault и SQLite согласуются staging/compensation протоколом, а не выдуманной общей транзакцией. `Merge` добавляет/обновляет членство. `Replace` заменяет состав выбранной коллекции после показа diff; не стирает общую историю и другие коллекции. Изменение username/session-параметра поставщика может означать новый доступ; endpoint-dedup недостаточен.

Решение по совместимости: существующие записи мигрируют в «Ранее собранные», с пометкой неизвестного происхождения там, где оно потеряно. Нельзя ретроспективно назвать их «только моими». Существующие команды и форматы сохраняют совместимость для поддержанных unauth записей. Исключения явно документируются: устранение скрытого DIRECT при пустом экспорте и ограничения private scope/freshness. Старый binary не пишет в новую schema. Rollback восстанавливает pre-migration snapshot, отдельно сохраняя новую БД, и не обещает lossless downgrade после создания новых данных.

## Правила принятия результатов

Профиль содержит обязательные probes M и дополнительные O. Успех: все M прошли и правило для O выполнено: `all`, `any` либо `at_least(K)`. Пустой optional-набор допустим только при явной политике `none`; `any` при O=0 и K>числа probes — ошибка настройки. Это исключает ошибочное превращение обязательной проверки в необязательную. В режиме пригодности нужен хотя бы один успешный effective probe; M=0/O=0, all-skipped и at_least(K≤0) не дают passed. Zero-probe допустим только в collect/diagnostic без допуска в рабочую выдачу.

`unknown` отличается от `fail`: контрольный endpoint недоступен, не хватило бюджета, неизвестна страна, измерение ещё не выполнено. Для выдачи «подходит» обязательные неизвестные не считаются успехом. При fail-fast непройденные проверки записываются как `skipped`, а не как выдуманные измерения. Оценка надёжности не сравнивает усечённые и полные наборы как равные.

Отбор для пула концептуально: принадлежит разрешённой коллекции → есть требуемая версия/совместимая семантика probe → не истёк срок → обязательные проверки прошли → ограничения страны/ASN соблюдены → нет исключения/cooldown → доступ разрешён → не исчерпаны connection limits. Только потом применяется ranking. Admission пересчитывается при каждой выдаче API и новом gateway connect, даже если generation не изменилась; публикация имеет своё время, каждое наблюдение — своё. Уже установленные соединения при обычном expiry продолжаются до закрытия; явный revoke может требовать отдельной политики разрыва. Выбор stale/failed записей для перепроверки отделён от отбора fresh записей потребителю.

При свежем отказе старый успех нельзя использовать как текущий. История остаётся видимой. В целевой модели смена сети создаёт новый network epoch и требует перепроверки перед обещанием актуальной пригодности; это не доказывает, что прокси сломан. Пока OS/network detection не реализована, R1 сообщает «проверено N минут назад в зафиксированных условиях», без обещания текущей сети; аномалия часов делает freshness uncertain.

## География без ложных обещаний

Отдельные поля: страна endpoint по GeoIP; заявленная поставщиком страна; наблюдавшаяся страна выхода; дата и версия базы. Не смешивать их в одном фильтре. Поиск по названиям на RU/EN, несколько включённых стран, исключения и явная политика unknown. «Нидерланды на выходе» при неизвестном выходе требует отдельного измерительного задания с judge-пробой; read-only фильтр не запускает сеть сам. Нельзя выбросить поискового кандидата только потому, что входной сервер в Германии. Hostname получает endpoint geo по наблюдённому resolved IP с временем; без него — unknown.

Квоты пула указывают базу измерения: endpoints или подтверждённые уникальные exit IP. Если выход неизвестен, подтвердить квоту уникальных выходов нельзя. ASN/organization полезны для фильтра и сравнения, но нынешняя hosting-эвристика не доказывает residential/mobile статус. IPv4/IPv6 у endpoint и доступность IPv4/IPv6 назначения — отдельные возможности.

## Подключение и постоянные пулы

Путь новичка: выбрать готовый список → «Подключить» → выбрать браузер/приложение/скрипт → получить точные настройки → выполнить короткий контроль через локальный gateway → увидеть результат, дату и кнопку восстановления предыдущих настроек, если приложение их меняло.

Стабильный локальный адрес gateway не означает стабильный внешний IP. Есть две политики сессии: `strict` закрепляет upstream и при его потере возвращает ошибку; `failover` разрешает смену upstream и выдаёт событие. Даже strict не гарантирует неизменный exit у ротирующего поставщика. Уже открытый TCP-туннель нельзя прозрачно перенести на другой upstream.

Контроллер пула сначала перепроверяет резерв, затем разрешённые ранее известные записи, затем дозагружает разрешённые источники в рамках бюджета. Временная ошибка ведёт в cooldown, позднее — probation с проверкой, затем возможен повторный допуск. Выпавшие элементы не исчезают навсегда. При нуле: явный `pool_empty`, backoff и уведомление при переходе; без автоматического DIRECT, замены страны и подмешивания публичного списка в частный.

## GUI, CLI и API

Один слой операций и правил: validate/import/submit job/select/publish pool/connect. UI и CLI преобразуют ввод в те же команды; API валидирует ту же схему. Предлагаемые новые имена/маршруты в карточках — проект интерфейса, не уже доступная документация.

GUI показывает задания и события; CLI получает JSON/NDJSON и exit codes; API — job IDs, cursor pagination и scoped tokens. Изменяющие вызовы требуют idempotency key; повтор после сетевого обрыва не создаёт двойной импорт/задание. Стартовая реализация может иметь одну активную проверку и очередь, сохраняя существующую модель одного writer. Много процессов, очередей сообщений или облако не требуются ради API.

## Ошибочные состояния

| Состояние | Сообщение пользователю | Предлагаемое восстановление |
|---|---|---|
| Пустой источник / неподдерживаемый формат | Что загружено, какой parser, сколько распознано | Preview, выбор адаптера; старую коллекцию сохранить |
| Ничего после фильтров | Числа до/после каждого фильтра, unknown отдельно | Одним действием ослабить конкретное условие, не менять скрыто |
| Target или сеть недоступны | Проверка недостоверна, причина и время контрольной пробы | Пауза/backoff; не ухудшать все upstreams автоматически |
| Auth отказ / хранилище закрыто | Нужен доступ к секрету либо неверные credentials | Обновить credential reference, перепроверить только затронутые записи |
| Сбой/сон | Что сохранено, что не завершено, что устарело | Resume по checkpoint + проверка сети и freshness |
| Пустой пул | Сколько нужно, почему дефицит, когда следующая попытка | Пополнение в рамках scope/budget, действия пользователя при исчерпании |
| Экспорт частично несовместим | Какие строки/свойства целевой формат не поддерживает | Другой формат или gateway; нельзя тихо удалять auth/DNS/TLS поля |
| Старые данные | Последняя проверка и граница пригодности | Перепроверка; history доступна отдельно от current |

## Продуктовые показатели

Измерять локально и по желанию экспортировать: время до первого *пригодного* результата и до N; долю успешно завершённых сценариев импорта/подключения; долю времени пула ниже N; причины дефицита; байты и попытки на одного допущенного участника; recovery после sleep/crash; число необъяснённых нулевых выдач. Для интерфейса полезнее воспроизводимый task completion, чем увеличение workers или размера каталога.

Никакой скрытой телеметрии. Численные целевые значения сначала устанавливаются на синтетическом стенде и коротких пользовательских пробах; текущих полевых данных для обещаний нет.
